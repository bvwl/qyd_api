# 项目统计功能 - 修复完成

## 问题描述

前端调用统计API时报错：
```
'str' object has no attribute 'executor_class'
```

## 问题原因

在 `app/crud/project/stats.py` 和 `app/utils/stats_sync.py` 文件中，错误地使用了 `db_read()` 和 `db_write()` 函数。

这两个函数返回的是 `QuerySet` 对象，而不是模型类本身。在某些情况下，代码尝试在 `QuerySet` 上调用不存在的方法，导致错误。

## 修复内容

### 1. 修复 `app/crud/project/stats.py`

移除了对 `db_read()` 和 `db_write()` 的使用，直接使用模型类：

**修改前**:
```python
from app.core.database import db_read, db_write

# 错误的使用方式
stats = await db_read(ProjectDailyStats).get_or_none(...)
projects = await db_read(ProjectInfo).filter(...).all()
```

**修改后**:
```python
# 正确的使用方式
stats = await ProjectDailyStats.get_or_none(...)
projects = await ProjectInfo.filter(...).all()
```

### 2. 修复 `app/utils/stats_sync.py`

同样移除了对 `db_read()` 和 `db_write()` 的使用：

**修改前**:
```python
from app.core.database import db_read, db_write

accounts = await db_read(ProjectAccount).filter(...).all()
deleted_count = await db_write(ProjectDailyStats).filter(...).delete()
```

**修改后**:
```python
accounts = await ProjectAccount.filter(...).all()
deleted_count = await ProjectDailyStats.filter(...).delete()
```

### 3. 修复数据库表创建

移除了外键约束，因为存在兼容性问题：

**修改前**:
```sql
CONSTRAINT `fk_project_daily_stats_project_id` 
FOREIGN KEY (`project_id`) REFERENCES `project_info` (`id`) ON DELETE CASCADE
```

**修改后**:
```sql
-- 移除外键约束，只保留索引
KEY `idx_project_daily_stats_project_id` (`project_id`)
```

### 4. 创建数据库表

使用简单的Python脚本创建表：

```bash
python backend/create_stats_table.py
```

### 5. 同步历史数据

## 关于 `db_read()` 和 `db_write()` 的使用

### 正确的使用方式

`db_read()` 和 `db_write()` 是为了支持读写分离而设计的工具函数。它们返回的是 `QuerySet` 对象，应该这样使用：

```python
from app.core.database import db_read, db_write

# ✅ 正确：用于需要读写分离的场景
users = await db_read(User).filter(status=1).all()
await db_write(User).filter(id=user_id).update(name="new_name")
```

### 何时不需要使用

对于简单的CRUD操作，直接使用模型类即可：

```python
# ✅ 推荐：简单的查询和操作
user = await User.get_or_none(id=user_id)
users = await User.filter(status=1).all()
await User.create(email="test@example.com")
```

### 项目统计功能的选择

项目统计功能不需要读写分离，因为：

1. 统计数据量不大
2. 查询频率不高
3. 有Redis缓存支持
4. 简化代码，减少复杂度

因此，我们选择直接使用模型类，而不是 `db_read/db_write`。
