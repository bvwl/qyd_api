# Redis管道分离设计

## 概述

为了提高系统的健壮性和可靠性，我们将Redis缓存操作和任务清理操作从数据库事务中分离出来，使用独立的管道进行处理。这样即使缓存操作失败，也不会影响核心的数据库操作。

## 设计原则

### 1. 关注点分离
- **数据库操作**: 核心业务逻辑，必须成功
- **缓存操作**: 性能优化，失败可容忍
- **任务清理**: 资源管理，失败可容忍

### 2. 故障隔离
- 缓存失败不影响数据库操作
- 任务清理失败不影响数据处理
- 每个操作独立处理异常

### 3. 可观测性
- 每个操作都有独立的日志
- 失败时记录警告而非错误
- 便于问题定位和监控

## 处理流程

### 完整流程图

```
┌─────────────────────────────────────────────────────────┐
│ 1. 检查缓存（独立管道）                                    │
│    - 批量检查Redis缓存                                     │
│    - 分离已缓存和未缓存的数据                               │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│ 2. 查询数据库（从库）                                      │
│    - 使用从库查询现有记录                                   │
│    - 准备更新和创建列表                                     │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│ 3. 数据库操作（主库，事务中）                              │
│    ┌─────────────────────────────────────────────────┐  │
│    │ BEGIN TRANSACTION                               │  │
│    │   - 批量更新记录                                 │  │
│    │   - 批量创建记录                                 │  │
│    │ COMMIT                                          │  │
│    └─────────────────────────────────────────────────┘  │
│    ✓ 成功 → 继续                                         │
│    ✗ 失败 → 重新加入队列，返回                            │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│ 4. 添加缓存（独立管道，独立异常处理）                       │
│    try:                                                 │
│      - 批量添加Redis缓存                                 │
│      - 设置过期时间                                      │
│    except:                                              │
│      - 记录警告日志                                      │
│      - 继续执行（不影响主流程）                           │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│ 5. 清理任务（独立管道，独立异常处理）                       │
│    try:                                                 │
│      - 批量删除任务数据                                  │
│    except:                                              │
│      - 记录警告日志                                      │
│      - 继续执行（不影响主流程）                           │
└─────────────────────────────────────────────────────────┘
                        ↓
                    完成处理
```

## 代码实现

### 1. 数据库操作（在事务中）

```python
# 数据库操作必须成功，使用事务保证一致性
async with in_transaction(connection_name="default"):
    if updates:
        await self.model_class.bulk_update(updates, fields=update_fields)
    
    if creates:
        await self.model_class.bulk_create(creates)

# 记录成功日志
logger.info(f"数据库操作成功，更新 {len(updates)}，创建 {len(creates)}")
```

**特点**:
- ✅ 在事务中执行
- ✅ 失败会回滚
- ✅ 失败会重新加入队列

### 2. 添加缓存（独立管道）

```python
# 缓存操作在独立的try-except中，失败不影响主流程
try:
    async with redis.pipeline() as cache_pipe:
        for key, operation in cache_items:
            cache_key = f"{cache_key_prefix}{key}"
            cache_pipe.setex(cache_key, cache_expire_seconds, operation)
        await cache_pipe.execute()
    
    logger.debug(f"缓存添加成功，缓存 {len(cache_items)} 条记录")
    
except Exception as cache_error:
    # 缓存失败只记录警告，不影响主流程
    logger.warning(
        f"缓存添加失败: {cache_error}，"
        f"数据库操作已成功，将继续处理"
    )
```

**特点**:
- ✅ 独立的管道
- ✅ 独立的异常处理
- ✅ 失败只记录警告
- ✅ 不影响数据库操作

### 3. 清理任务（独立管道）

```python
# 任务清理在独立的try-except中
try:
    async with redis.pipeline() as delete_pipe:
        for key in keys_to_process:
            delete_pipe.delete(key)
        await delete_pipe.execute()
    
    logger.debug(f"任务清理成功，清理 {len(keys_to_process)} 个任务")
    
except Exception as delete_error:
    # 删除失败只记录警告
    logger.warning(f"任务清理失败: {delete_error}")
```

**特点**:
- ✅ 独立的管道
- ✅ 独立的异常处理
- ✅ 失败只记录警告
- ✅ 不影响数据库操作

## 优势分析

### 1. 提高可靠性

**场景**: Redis缓存服务暂时不可用

**传统方式**:
```
数据库操作 → 添加缓存（失败）→ 整个事务回滚 → 数据未保存
```

**分离方式**:
```
数据库操作（成功）→ 添加缓存（失败，记录警告）→ 数据已保存
```

**结果**: 数据库操作成功，只是缓存未添加，下次处理时会重新查询数据库

### 2. 提高性能

**场景**: 缓存操作较慢

**传统方式**:
```
BEGIN TRANSACTION
  数据库操作
  等待缓存操作完成  ← 事务持有锁
COMMIT
```
事务时间长，锁持有时间长

**分离方式**:
```
BEGIN TRANSACTION
  数据库操作
COMMIT                ← 快速释放锁
缓存操作（异步）
```
事务时间短，锁持有时间短

### 3. 更好的可观测性

**日志示例**:

```
# 成功场景
[Worker-0] 数据库操作成功，更新 150，创建 50
[Worker-0] 缓存添加成功，缓存 200 条记录
[Worker-0] 任务清理成功，清理 200 个任务
[Worker-0] 成功处理 200 条数据，更新 150，创建 50，跳过缓存 100

# 缓存失败场景
[Worker-0] 数据库操作成功，更新 150，创建 50
[Worker-0] 缓存添加失败: Connection timeout，数据库操作已成功，将继续处理
[Worker-0] 任务清理成功，清理 200 个任务
[Worker-0] 成功处理 200 条数据，更新 150，创建 50，跳过缓存 100

# 任务清理失败场景
[Worker-0] 数据库操作成功，更新 150，创建 50
[Worker-0] 缓存添加成功，缓存 200 条记录
[Worker-0] 任务清理失败: Redis connection lost
[Worker-0] 成功处理 200 条数据，更新 150，创建 50，跳过缓存 100
```

每个操作的状态都清晰可见

## 故障场景分析

### 场景1: 缓存服务不可用

**影响**:
- ✅ 数据库操作正常
- ⚠️ 缓存未添加
- ⚠️ 下次相同数据会重新查询数据库

**恢复**:
- 缓存服务恢复后，新数据会正常缓存
- 旧数据在缓存过期后会重新缓存

**监控**:
```bash
# 查看缓存失败日志
tail -f backend/logs/app.log | grep "缓存添加失败"
```

### 场景2: 任务清理失败

**影响**:
- ✅ 数据库操作正常
- ✅ 缓存添加正常
- ⚠️ 任务数据未删除（占用Redis内存）

**恢复**:
- 任务数据有过期时间（24小时）
- 会自动清理

**监控**:
```bash
# 查看任务清理失败日志
tail -f backend/logs/app.log | grep "任务清理失败"

# 查看Redis内存使用
redis-cli INFO memory
```

### 场景3: 数据库操作失败

**影响**:
- ❌ 数据库操作失败
- ⚠️ 任务重新加入队列
- ⚠️ 会自动重试（最多3次）

**恢复**:
- 自动重试机制
- 重试失败后记录错误日志

**监控**:
```bash
# 查看数据库操作失败日志
tail -f backend/logs/app.log | grep "数据库操作失败"
```

## 最佳实践

### 1. 监控告警

**关键指标**:
- 缓存失败率
- 任务清理失败率
- 数据库操作失败率

**告警阈值**:
```yaml
缓存失败率 > 10%: 警告
```

```bash
grep "缓存添加失败" backend/logs/app.log | wc -l
```


|------|---------|---------|
| 缓存失败 | 数据未保存 | 数据已保存 |

## 总结

通过将缓存操作和任务清理操作从数据库事务中分离出来，使用独立的管道进行处理，我们实现了：

1. **更高的可靠性**: 缓存失败不影响数据库操作
2. **更好的性能**: 减少事务持有时间
3. **更强的可观测性**: 每个操作独立记录日志
4. **更好的故障隔离**: 各个操作独立处理异常

这种设计遵循了"关注点分离"和"故障隔离"的原则，使系统更加健壮和可维护。

## 注意事项

1. **缓存一致性**: 如果缓存添加失败，下次相同数据会重新查询数据库
2. **内存管理**: 如果任务清理失败，需要定期手动清理
3. **监控告警**: 需要监控各个操作的失败率
4. **日志分析**: 定期分析日志，发现潜在问题

通过合理的监控和维护，这种设计可以大大提高系统的可靠性和性能。
